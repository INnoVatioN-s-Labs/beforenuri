# `test.md` 변경 설명서

## 1. 이 문서의 목적

이 문서는 [test.md](/Users/koyoungseok/Desktop/t4lk/t4lk/src/main/test.md)에 어떤 내용을 추가했는지, 왜 추가했는지, 기존 초안에서 무엇을 삭제하거나 정리했는지를 이해하기 쉽게 설명하기 위한 문서입니다.

핵심은 단순히 문서를 길게 만든 것이 아니라, 실제 구현할 때 필요한 판단 기준을 문서 안에 넣었다는 점입니다.

## 2. 기존 문서 상태

기존 `test.md`는 아래 성격의 초안이었습니다.

1. 서비스 아이디어와 큰 방향은 잘 잡혀 있었다.
2. RDB, MongoDB, WebSocket 같은 핵심 키워드도 이미 포함되어 있었다.
3. 하지만 문서가 중간에서 끝나 있었고, 구현자가 바로 작업에 들어가기엔 빠진 정보가 많았다.

예를 들어 기존 문서에는 이런 한계가 있었습니다.

1. "어떤 API가 필요한지"가 구체적으로 정리되어 있지 않았다.
2. "WebSocket에서 어디로 보내고 어디를 구독하는지"가 완전한 형태로 정리되어 있지 않았다.
3. "예외 상황을 어떻게 처리할지"가 없었다.
4. "보안상 어떤 점을 조심해야 하는지"가 약했다.
5. "지금 프로젝트 상태에서 다음에 무엇부터 구현해야 하는지"가 정리되어 있지 않았다.

그래서 이번 수정의 목적은 초안을 "설명용 문서"에서 "구현 기준 문서"로 바꾸는 것이었습니다.

## 3.5. `5. 데이터 모델 설계`

### 추가한 이유

기존 문서에도 테이블/컬렉션 설명은 있었지만, 일부 컬럼이 빠져 있었고 운영상 필요한 정보가 조금 약했습니다.

### 추가한 기능

다음 내용을 더 구체화했습니다.

1. `chat_room.description`
2. `chat_room.updated_at`
3. `nickname_word.is_active`
4. MongoDB 예시 필드명 정리
5. 인덱스 전략 설명

### 각 추가 항목의 역할

- `description`:
  방 제목만으로 부족할 때 설명 문구를 둘 수 있습니다.
  예: "20대 자유 대화", "지역별 잡담방"

- `updated_at`:
  방 정보가 언제 수정됐는지 추적할 수 있습니다.
  관리자 기능이 붙을 때 유용합니다.

- `is_active`:
  닉네임 단어를 운영 중 비활성화할 수 있습니다.
  부적절한 단어 제거에 도움이 됩니다.

- MongoDB `messageType`:
  일반 채팅과 입장/퇴장 같은 시스템 메시지를 구분할 수 있습니다.

- 인덱스 전략:
  단순히 저장하는 게 아니라, 조회 성능까지 생각했다는 뜻입니다.

### 왜 중요한가

DB 설계는 "저장만 되면 끝"이 아닙니다.
운영, 조회 성능, 관리자 기능까지 고려해야 실제 서비스 구조가 됩니다.

## 3.7. `7. API 및 WebSocket 설계`

### 추가한 이유

이 부분이 가장 중요하게 추가된 섹션 중 하나입니다.
기존 문서에는 흐름 설명은 있었지만, 실제 구현 가능한 인터페이스 수준까지는 내려와 있지 않았습니다.

### 추가한 기능

다음 내용을 새로 명시했습니다.

1. `POST /api/session/anonymous`
2. `GET /api/rooms`
3. `GET /api/rooms/{roomId}`
4. `GET /api/rooms/{roomId}/messages`
5. WebSocket endpoint `/ws`
6. STOMP subscribe 경로 `/topic/rooms/{roomId}`
7. STOMP publish 경로 `/app/rooms/{roomId}/chat`
8. 요청/응답 JSON 예시

### 각 항목의 역할

- 익명 세션 발급 API:
  사용자가 처음 들어왔을 때 이름과 토큰을 받습니다.

- 방 목록/상세 조회 API:
  프론트가 입장 가능한 방을 보여줄 수 있습니다.

- 메시지 조회 API:
  실시간 소켓만으로는 과거 내역을 불러올 수 없기 때문에 필요합니다.

- `/ws`:
  웹소켓 연결 시작점입니다.

- `/topic/rooms/{roomId}`:
  사용자가 특정 방 메시지를 구독하는 주소입니다.

- `/app/rooms/{roomId}/chat`:
  사용자가 메시지를 서버로 보내는 주소입니다.

### 왜 중요한가

아키텍처 문서가 실제 구현 문서가 되려면, "컴포넌트 이름"이 아니라 "통신 계약"이 있어야 합니다.
이 섹션이 바로 그 계약입니다.

예전 문서의 일부 설명은 아이디어 차원에서는 좋았지만, 바로 구현으로 연결되기 어려운 문장이 있었습니다.

### 왜 그렇게 했는가

이번 문서의 목적은 "서비스 컨셉 소개"보다 "개발 기준 수립"이기 때문입니다.
그래서 추상 표현은 줄이고, API/정책/흐름/예외처럼 바로 쓰일 수 있는 내용으로 바꿨습니다.

---

## 5. 가장 중요한 변화 요약

이번 수정에서 가장 중요한 변화는 아래 5개입니다.

1. 문서를 완결된 구조로 다시 만들었다.
2. API와 WebSocket 경로를 구체적으로 적었다.
3. DB 설계에 운영용 필드와 인덱스 의도를 보강했다.
4. 실패 처리, 보안, 운영 정책을 문서에 넣었다.
5. 지금 프로젝트에서 다음에 무엇을 구현해야 하는지 연결했다.

즉, 이전 문서는 "아이디어가 담긴 초안"에 가까웠고, 지금 문서는 "개발 기준서"에 더 가깝습니다.

## 6. 다음에 이어서 할 수 있는 작업

이 문서를 바탕으로 바로 이어서 가능한 작업은 아래와 같습니다.

1. `build.gradle`에 필요한 의존성 추가
2. `room`, `session`, `chat` 패키지 뼈대 생성
3. 익명 세션 발급 API부터 구현
4. MongoDB 메시지 document 및 조회 API 구현

원하면 다음 단계로는 이 설명서를 기준으로 실제 코드 구조까지 바로 만들어 줄 수 있습니다.
